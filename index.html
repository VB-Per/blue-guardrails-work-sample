How I’d introduce Blue Guardrails to engineers

I’m Vighnesh Suresh Babu. I write about technical products for the engineers who use them. I’m based in Berlin and I’m applying to be your Founding Technical Marketing Manager.

How to detect hallucinations in AI agents in production

At the middle of the funnel, the engineer’s question changes. “Would this catch a mistake in my agent?” I wrote this guide and built a Python example they can run on a laptop. It uses a shop order so anyone can check the result without knowing anything about medicines.

Read the technical article and its sources

“Your order A-77 is on its way.” The customer had asked for tracking. The agent had just looked up A-78 and received an error. Its reply switched back to the customer’s order number and reported that the order had shipped.

Run python3 run.py -v in the extracted companion code and find 03_wrong_tool_argument. The record shows exactly what evidence the agent had when it answered. It also leaves one question open. Was A-77 actually on its way? To find out, check the fulfilment record for A-77.

Agents fail where RAG checks do not look

A tool returns {"stock": 0} and the agent says the item is in stock. The contradiction is visible in a single exchange. In a longer run, an answer may depend on a search that came back empty six steps earlier. To find the mistake, follow the answer back to the step that supplied its evidence.

Most hallucination detectors were built for RAG (retrieval-augmented generation, where the model answers from documents fetched for the question). An agent builds its context as it runs, by calling tools such as an order lookup. Its errors also land in tool arguments, and one early mistake can lead to later steps that agree with each other and are all wrong.

Check each output against the trace, not the truth

A trace records a single run. Its spans describe operations such as model calls and tool calls. To check an answer, capture the relevant instructions, messages and tool results. Then ask what the agent could support at the moment it made each claim or chose each argument. Blue Guardrails’ issue detection uses the agent’s input as the reference for this check.

So a hallucination here is output that the agent's context at that step does not support, and a trajectory is the ordered sequence of steps in one run. Attribute names follow the OpenTelemetry GenAI semantic conventions, the open standard for recording model and tool calls as spans.

Use a different check at each level

Claims: split the answer, then check each part

Break the answer into claims (single statements of fact) and check each against the trace up to that span, as FActScore does with atomic facts. Match numbers, dates and IDs against tool results in code, at no token cost. Send paraphrase and inference to an LLM verifier, a model prompted to judge whether the evidence supports each claim.

Where it breaks:

  • Checks built for short text miss errors in long answers. In Blue Guardrails' comparison of seven detectors on its pharma dataset PlaceboBench, RAGAS (GPT-5.2 as judge) checked answers sentence by sentence and reached 62.0% message-level accuracy (one right-or-wrong verdict per answer); the post says splitting "discards cross-sentence relationships". Three claim-level tools, which flag individual claims (Azure Groundedness Detection, Google Cloud Check Grounding, MiniCheck), reached 22% to 24% F1. F1 combines missed errors and false alarms (100% is perfect); at 22% to 24%, most errors were missed, most flags were wrong, or both. The post ties this to NLI models, trained on short sentence pairs to judge whether one sentence follows from another.
  • Long contexts hide subtle errors. PlaceboBench prompts had a median of 13,668 input tokens, and one error type was a rare side effect reported as common.
  • Supported and true are different tests. World-knowledge errors (facts from the model's training, not the context) were PlaceboBench's second most frequent type. If answers must come only from the context, flag them even when correct.

Tool calls: validate the schema, then where each value came from

gen_ai.tool.definitions lists each tool's parameters as a JSON Schema (a standard format for allowed fields, types and values), so a standard validator can check every call, including enum values (the fixed list a field accepts). A well-formed wrong value still passes, so check provenance: treat an ID, order number, email or path found in no user message, system instruction or earlier tool result as invented. Derived values, such as date ranges, need an allowlist.

Where the agent acts on an environment you can inspect, check preconditions first. StateMirror does this for coding agents: it extracts predicates such as file_exists(/repo/reproduce.py) from each proposed action and checks them against the live repository, with no model call. Wrong, unnecessary or missing calls need a judge that sees the request, the tool descriptions and the call. In AgentHallu, tool-use errors were the hardest category to localise (pin to the step where they happened).

Where it breaks: a plausible wrong value passes both cheap checks, and checking after execution is too late for side effects, so check tools that write before they run.

Steps: link each tool result to the answer that relies on it

Each tool call carries an ID that links it to its result (id on tool_call and tool_call_response parts, gen_ai.tool.call.id on execute_tool spans). Use it to flag an answer stating facts that a failed or empty call was meant to provide, and success language after a failed write.

For deeper checks, keep a claim ledger. The DRIFT auditor records when each claim enters the run, when it starts to matter and which later spans depend on it, then traces unsupported claims to their origin. On the verified TELBench set, the authors report that DRIFT raised GPT-5.4’s span-level macro-F1 by 18.55 points over direct prompting. Also check late steps against the system instructions, because models miss details in earlier messages as context grows ("context rot", in Blue Guardrails' docs).

Where it breaks: knowing that a run went wrong is easier than knowing where. DRIFT's authors write that auditors "still struggle to pinpoint the earliest annotated error span", and 36.9% of successful runs in their corpus contained process errors, more than one in three.

LLM judges: one narrow rule per issue, flagged spans as output

LLM-as-a-judge means asking a model to grade an output. Write each issue type as a narrow rule that names the evidence, like dosage_error in Blue Guardrails' evaluator guide: "The response gives a medication dosage, unit, administration frequency, or maximum daily limit that conflicts with the provided source." Add domain context: what the application does, which sources it uses, what counts as an issue. Ask for flagged spans with a label and an explanation: a verdict per message only lets you discard the response, while an explained span says what to fix.

Where it breaks: judges favour answers for where they appear, for length and for being their own (position, verbosity and self-enhancement bias, Zheng et al.). Shuffle the order and judge each sample several times, as Blue Guardrails' agentic RAG comparison did with five judgements per sample. Shankar et al. name the deeper limit: "LLM-generated evaluators simply inherit all the problems of the LLMs they evaluate."

The code: OpenTelemetry spans in, flagged issues out

The GenAI conventions are at Development status (they can still change) and now live in a separate repository. Message content is opt-in. The example uses synthetic data. For a real application, first choose which fields your team can retain and how it will protect sensitive content.

import json, re
from jsonschema import Draft7Validator  # pip install jsonschema

# Argument names whose values must come from the conversation, not the model
GROUNDED_ARG = re.compile(r"(^|_)(id|number|email|path|sku)$")

def attr(span, key, default=None):
    v = span["attributes"].get(key, default)
    return json.loads(v) if isinstance(v, str) and v[:1] in "[{" else v

def parts(messages, kind):
    return [p for m in messages or [] for p in m.get("parts", []) if p.get("type") == kind]

def check_trace(spans):
    """spans: one trace (or one gen_ai.conversation.id), exported with flattened attributes."""
    issues, bad_steps = [], {}
    for s in sorted(spans, key=lambda s: s["start_time"]):
        a, op = s["attributes"], s["attributes"].get("gen_ai.operation.name")

        if op == "execute_tool":
            result = attr(s, "gen_ai.tool.call.result")
            if a.get("error.type") or result in (None, "", [], {}):
                bad_steps[a.get("gen_ai.tool.call.id")] = a["gen_ai.tool.name"]

        elif op == "chat":
            seen = json.dumps([attr(s, "gen_ai.system_instructions", []),
                               attr(s, "gen_ai.input.messages", [])], ensure_ascii=False)
            tools = {t.get("name"): t for t in attr(s, "gen_ai.tool.definitions", [])}
            out = attr(s, "gen_ai.output.messages", [])

            for call in parts(out, "tool_call"):
                args, tool = call.get("arguments") or {}, tools.get(call.get("name"))
                if tool is None:
                    issues.append(("unknown_tool", s["span_id"], call.get("name")))
                    continue
                for err in Draft7Validator(tool.get("parameters") or {}).iter_errors(args):
                    issues.append(("schema_violation", s["span_id"], err.message))
                for k, v in args.items():
                    if GROUNDED_ARG.search(k) and str(v) not in seen:
                        issues.append(("ungrounded_argument", s["span_id"], f"{k}={v}"))

            # Candidate, not verdict: send to the LLM verifier with the failed step attached
            if bad_steps and parts(out, "text"):
                issues.append(("answer_after_failed_step", s["span_id"], sorted(set(bad_steps.values()))))
    return issues

On a test trace where the user asks about order A-77, this flags get_order(order_id="A-78", include="tracking") twice (tracking is not an allowed value; the user never gave A-78) and flags the final answer for review because it follows the failed call. The companion repo adds three more traces, a claim check and tests.

Longer runs are harder. In AgentHallu, GPT-5's localisation accuracy falls from 40.3% on runs of five steps or fewer to 23.9% on eleven or more: about one time in four. On FaithBench summaries where popular detectors disagreed, the best were near 50% accuracy, a coin toss. In a test of five reference-free methods on six RAG datasets, some were consistently strong and others not much better than random chance on some datasets (Sardana), so test on your own data.

Run cheap checks inline and model checks in the background

  • Deterministic checks (code rules that give the same result every time: schema, provenance, failed steps) take milliseconds and no tokens; StateMirror's median was 1.50 ms. Run them inline on every span.
  • LLM verification costs seconds and tokens: the judges in the StateMirror study took a median of 14.51 s to 17.73 s and 1.9K to 19.2K tokens per action. Run it asynchronously (off the request path), on a sample or on every answer, and synchronously only where an answer goes straight to a user in a high-stakes domain.
  • Trajectory judging reads the whole run, and better localisation costs more: in AgentHallu, step-by-step prompting raised average localisation from 24.3% to 36.6% and average input tokens from 6,312 to 17,514, almost three times as many. Run it on a sample, or on runs the cheaper checks flagged.

Compare that with the agent's own time: in Blue Guardrails' agentic RAG comparison, model time per task averaged 11.2 s for naive RAG and 44.6 s for the hybrid graph-and-vector setup, so a 10-second synchronous check adds about 90% to the first and about 22% to the second.

Blue Guardrails runs both timings on one engine: asynchronous detection on traces sent over OTLP (the OpenTelemetry export protocol), and a live detection API (POST /v1/evaluate) that returns flagged text, label, explanation and offsets, for checks before an answer is shown or in CI test runs. A verifier reads everything the agent read, so where it runs matters: Blue Guardrails runs as EU-hosted SaaS, in a private cloud or on-premises.

When a check fires: flag, replay, steer or block

  1. Flag and aggregate. Store span, label, explanation and step, and track the rate per issue type. A jump after a model or prompt change signals a regression.
  2. Replay a fix on past traces. Blue Guardrails' experiments use "n-1 replay": every message except the final assistant message becomes context, a new model writes the final one, and detection runs again. You compare issue rate and cost on up to 300 real conversations (docs) with no gold dataset, because each new answer is scored against the same context. Earlier tool results stay frozen, so this tests the final generation only.
  3. Steer mid-run. Return the issue to the agent before the answer or next action ships. In Blue Guardrails' steering experiment, an evaluator fed system prompt deviations, missed nodes and hallucinations back to a knowledge-graph extraction agent (at most two correction loops). Against a reference graph of seven medicines, node recall (the share of expected entities found) rose from 58% to 72% for GPT 5.4 Nano and from 83% to 91% for Deepseek v4 Flash. Gains across models and metrics were 4 to 14 percentage points (their own result); the post does not report the latency each loop adds.
  4. Block. Keep this for irreversible actions you cannot correct in time.

Test your detector on 100 to 300 of your own traces

Sample 100 to 300 traces across routes, tools and models, including runs your checks flagged and passed. Label span, issue type and step. PlaceboBench review took 10 to 20 minutes per response, so 200 responses take 33 to 67 hours; multi-step runs take longer.

Before scoring a detector, have two annotators label a shared subset and measure agreement (Cohen's kappa corrects it for chance). AgentHallu's annotators first agreed on the responsible step 77.9% of the time, so they disagreed on about one run in five. Where they disagree, rewrite the issue definition; Shankar et al. call this "criteria drift", as people refine what counts as an error while they label.

Report precision (the share of flags that were real issues) and recall (the share of real issues flagged) per failure type. One accuracy number hides the base rate: Blue Guardrails notes that flagging every PlaceboBench response as hallucinated would score about 45%. It also hides uneven coverage: in AgentHallu, Gemini-2.5-Pro localised reasoning hallucinations 64.4% of the time and tool-use hallucinations 14.6%. For trajectories, also score whether it flagged the right step and the first wrong one.

Review detector-only flags before counting them as false positives: labels miss things too. Re-annotating 408 data points from RAGTruth (nearly 18,000 RAG answers with word-level labels), Blue Guardrails found 865 hallucinations where the original labels had 86, about ten times as many (RAGTruth++, their own result). Rerun the validation whenever the detector's model, prompt, labels or domain context change.

FAQ

What is a hallucination in an AI agent?

Output that is not supported by what the agent had at that step: an unsourced claim, a tool argument found nowhere in the conversation, or a step built on a failed or misread result.

How do you detect hallucinations in an AI agent in production?

Check each output against the agent's trace at three levels: claims, tool-call arguments and steps. Run deterministic checks inline on every span and an LLM verifier with narrow rules asynchronously. Validate both against human-labelled traces.

How do you detect tool-call hallucinations?

Validate each call against the tool's JSON Schema, then check that every ID, order number, email or path in the arguments appears earlier in the trace. Check preconditions before tools that write. Wrong or missing calls need an LLM judge that sees the request and tool descriptions.

Can you detect agent hallucinations without a gold dataset?

Yes, for errors against the input context. When the relevant inputs are recorded, you can check whether they support a claim or tool argument without reference answers. You still need a small human-labelled sample to measure the detector itself.

How is hallucination detection for agents different from RAG?

RAG detection checks one answer against retrieved documents. Agent detection also checks tool calls and follows errors across steps, where one failed lookup can make later steps wrong but consistent. In AgentHallu, the best setup found the responsible step in 42.7% of cases.

Is LLM-as-a-judge reliable for hallucination detection?

The method around the model matters as much as the model. On the same PlaceboBench data, two LLM-based detectors reached 62.0% (RAGAS with GPT-5.2) and 94.4% (Blue Guardrails' verification agent, the vendor's own result) message-level accuracy. Use narrow rules, domain context and span-level output, validated against human labels.

How much latency does hallucination detection add?

On its coding-agent benchmark, StateMirror reported a median of 1.50 ms for its pre-execution check. The study’s model judges took seconds. Measure your implementation on the traffic it will handle. Run deterministic checks inline and LLM verification asynchronously, except at high-stakes points.

How do I know if my hallucination detector works?

Label 100 to 300 of your own traces with two annotators, check that they agree, then measure precision and recall per failure type. Repeat whenever the detector's configuration changes.

The checks (checks.py)

  1. tool_args: validates each tool_call against the JSON Schema in gen_ai.tool.definitions (type, enum, required, properties, additionalProperties, items). Then provenance: an argument named *id, *number, *email, *path or *sku must appear in the system instructions, a user message or an earlier tool result.
  2. claims: pulls dates, IDs, numbers and capitalised names out of each answer and looks for each one in what the agent saw at that step. 39.90 matches 39.9, November 20 matches 2026-11-20.
  3. trajectory: links tool calls to results by gen_ai.tool.call.id. A call with error.type or an empty result is a failed step. An answer after a failed step is flagged unless it says the step failed, or a later call of the same tool succeeded.

The model's own earlier output never counts as evidence, so an ID it invented in step 1 cannot support step 2.

Optional LLM judge, off by default. Some errors have nothing to match: in trace 02, "in stock" contradicts "stock": 0 with no number in the sentence. check_trace(spans, judge=fn) sends each answer and its evidence to fn as one prompt (judge_prompt: one narrow issue type, domain context, flagged spans with a label and explanation). llm_judge_stub only raises NotImplementedError. Trace format

Each file holds one trace: trace_id, a _note describing the scenario, labels (the planted failures, used by the tests) and spans. Spans use flattened attributes (span_id, start_time, attributes as a dict), the same shape as the snippet in the article. Raw OTLP JSON stores attributes as key/value lists, so flatten them first. Structured values can be objects or JSON strings; attr() reads both.

Attribute names follow the OpenTelemetry GenAI semantic conventions, checked on 27 Nov 2026 against the semantic-conventions-genai repository, where opentelemetry.io now points: gen_ai.operation.name (invoke_agent, chat, execute_tool), gen_ai.system_instructions, gen_ai.input.messages and gen_ai.output.messages (message parts of type text, tool_call and tool_call_response), gen_ai.tool.definitions, gen_ai.tool.name, gen_ai.tool.call.id, gen_ai.tool.call.arguments, gen_ai.tool.call.result, error.type. The conventions are at Development status, and every content attribute is opt-in: if your instrumentation does not capture content, these checks have nothing to read.

Differences from the snippet in the article

  • A small built-in schema validator instead of jsonschema, so nothing needs installing. Use jsonschema for real schemas.
  • Evidence leaves out the model's own earlier messages.
  • The claim check for numbers, dates, IDs and names is new; the article describes it but the snippet does not include it.
  • The trajectory rule links failures by call ID, skips answers that admit the failure, and clears a failure after a successful retry.

Limits

  • It is a teaching example, not a detector to deploy. The patterns are tuned to four synthetic traces. On real traffic expect false positives (a greeting with the user's name, "within 24 hours" from a policy the prompt lacks, a total the model computed correctly) and misses (claims with no number, date, ID or name, a wrong year, paraphrase, conflation, drift from the system prompt).
  • It checks support, not truth. A claim is "supported" if the agent saw it, even if the tool result was wrong.
  • Real detection needs domain context and an evaluated judge: what the application does, which sources count, what counts as an issue there, and a verifier measured against human labels on your own traces. The article's validation section covers how.
  • It is not Blue Guardrails' product and does not show how their detector works. It is an independent example by Vighnesh Suresh Babu, not affiliated with or endorsed by Blue Guardrails.
  • No model produced these traces. They are hand-written; demo-model and demo are placeholders.
